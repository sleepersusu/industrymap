## Context

品類節點側已於 `add-item-listing-and-amendment` 補上列表端點（`GET /api/products`，
分頁 + 名稱模糊搜尋 + `includeDrafts`），公司側尚無對應能力：`GET /api/companies/{code}`
必須先知道代號。

資料庫現況：52 家公司、85 筆供應角色、47 個品類節點。資料都在，缺的只是入口。

本次刻意排在前端開工之前——導覽結構取決於有沒有公司入口，事後補會需要改動已成形的資訊架構。

**並行注意**：另有進行中的 `fix-cross-exchange-identifier-lookup` 同樣涉及 `company-registry`。
本 change 的 delta **只 ADD 新 requirement**，不改動既有的「公司查詢以代號為對外識別」
與識別碼相關條目，兩份 delta 因此不會衝突。

## Goals / Non-Goals

**Goals:**
- 讓地圖能從公司側進入，而不只從產品往下展開
- 回答「某國有哪些公司在做這個零件」——跨產品彙總，這是既有端點做不到的
- 與 `GET /api/products` 的分頁、搜尋、審核可見範圍慣例完全一致

**Non-Goals:**
- 不做公司的修改與刪除（品類節點的修正端點另有其 change，公司側需求尚未出現）
- 不做「從公司展開其所有供應零件」的樹狀視圖——那是前端的組合查詢，先確認需求形狀再說
- 不做前端

## Decisions

### D1：沿用 `GET /api/products` 的既有慣例，不另立一套

分頁參數、`PageResponse` 外殼、`includeDrafts` 語意、空結果回空清單而非 404——
全部照既有做法。

- **理由**：兩個列表端點是同一類東西，前端會同時用到；形狀不一致會讓前端寫兩套處理邏輯
- **具體**：查詢條件收斂成 `CompanyQuery` payload 以 `@ModelAttribute` 綁定
  （對齊 `.claude/rules/api-design.md`「查詢條件也用 payload」）

### D2：搜尋同時比對名稱與別名，且結果去重

公司別名（台積電／TSMC／台灣積體電路製造股份有限公司）是既有設計的一部分，
搜尋只比對名稱會讓使用者以 TSMC 查不到台積電——而別名存在的意義正是為此。

- **採用**：查詢時 join 別名表，以正規化後的關鍵字對名稱與別名做包含比對，結果以公司去重
- **風險**：join 後同一公司可能因多個別名命中而重複，**總筆數也會跟著算錯**。
  分頁的總筆數若含重複，前端的「共 N 家」與頁數都會是錯的，因此去重必須在
  count 與內容兩邊都成立，不能只在回傳前濾一次

### D3：依供應零件過濾走 `company_item_role`

「這個零件有哪些公司在做」既有的 `GET /api/items/{id}/suppliers` 已能回答，
但它固定以零件為主體、回傳的是供應關係。本端點以公司為主體，且可與國別、
名稱關鍵字併用——用途不同，不是重複。

- **採用**：以 `company_item_role` 為過濾條件，公司去重
- **審核可見範圍的細節**：過濾時 MUST 只採計可見的供應角色。
  若以草稿角色也讓公司出現，會出現「公司已驗證但它其實只有草稿關係」的誤導結果

### D4：不對零件做遞迴展開

指定零件過濾時只比對**該節點本身**的供應角色，不遞迴其下層零件。

- **理由**：「做 PCB 的公司」與「做 PCB 底下所有材料的公司」是兩個不同問題，
  混在同一個參數裡呼叫端無從區分
- 日後若需要，以獨立參數表達，不改變本次語意

## Risks / Trade-offs

- **別名 join 造成的重複與計數錯誤** → 見 D2，count 與內容都必須去重，且需有測試明確覆蓋
  「名稱與多個別名同時命中」的情境
- **與 `fix-cross-exchange-identifier-lookup` 並行** → 本 change 只 ADD requirement，
  不碰既有條目；程式面兩者都會動 `CompanyController` 與 `CompanyService`，
  實作時先確認該 change 是否已合入，必要時後做者負責整併
- **查詢效能** → 名稱模糊比對與別名 join 在 52 家公司的規模下無虞；
  資料量成長後再依實際查詢計畫補索引，本次不預先優化

### D5：國別以不分大小寫的精確比對

`company.country` 型別上是自由字串，但實測既有 52 筆資料**全部是 ISO 3166-1 兩碼**
（TW 38、US 9、JP 3、DE 1、HK 1），沒有 `Taiwan` 這類混寫。

- **採用**：精確比對但不分大小寫（`tw` 與 `TW` 視為相同），不做模糊比對
- **理由**：模糊比對會讓 `US` 誤命中其他含該字母序列的值；既然資料已是兩碼，精確比對就夠
- **不在本次收斂為 enum**：寫入端仍接受自由字串，改成受控清單屬於寫入側的規範調整，
  範圍與風險都不同，不混進查詢功能
