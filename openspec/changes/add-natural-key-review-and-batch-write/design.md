## Context

上一個 change（`add-review-endpoints-and-seed-walkthrough`）以手動建一台腳踏車的方式走查了
整套 API，共約 30 筆資料。走查記錄了四項發現（F1–F4），本 change 處理其中三項：

- **F1（阻塞）**：審核端點以「類型 + 內部 id」定位，但 `CompanyIdentifierResponse` 不含 id、
  組成關係無 GET 端點、`ComponentNode` 只給 `itemId`。公司識別碼這一類**無法經 API 審核**，
  上次靠直接查資料庫才完成。
- **F2**：`SupplierResponse.companyReference` 給正規化名稱，`CompanyResponse.reference` 給主要代號，
  同一概念兩個值。
- **F4**：建立端點不支援批次，30 筆就要自行從各回應收集 id。

F3（找不到可查證的市佔率來源）不在本次範圍，屬資料來源問題而非介面問題。

本 change 的定位是 **AI 生成 pipeline 的前置**：pipeline 一次產生數百筆，目前介面在該規模下
無法使用。先修介面，pipeline 才有合理的呼叫對象。

## Goals / Non-Goals

**Goals:**
- 讓八類內容資料全部能經 API 完成審核，不需要任何資料庫存取
- 讓「建立 → 審核」能以兩次呼叫完成，不需在中間自行收集識別資訊
- 消除同一概念在不同回應給出不同值的情況

**Non-Goals:**
- 不做 AI 生成流程本身
- 不做商工登記批次匯入
- 不做前端與權限控管
- 不移除既有的 id 定位方式（既有呼叫端與測試不應被迫改寫）

## Decisions

### D1：審核改收自然鍵，而非在查詢回應補上內部 id

F1 的死結是兩條原則相撞：審核需要定位，查詢刻意不給 id。

- **採用**：審核端點支援自然鍵定位，各類型的自然鍵即其資料庫唯一鍵（見 spec 表格）
- **理由一**：「不曝露內部自增 id」原則的原意是**公司的路徑識別**（見 `company-registry`
  既有 requirement），把它擴張成「所有回應都不給 id」是過度推論；但既然自然鍵這條路可行，
  就不需要去挑戰那條原則
- **理由二（更重要）**：AI 生成流程產出的是**名稱與代號**，不是 id。若審核靠 id，
  pipeline 每寫入一筆就要回頭記住一個 id，或事後再查一次。自然鍵讓 pipeline 的輸出可以
  直接餵進審核，少一整層狀態管理
- **替代方案**：各查詢回應補上 id → 實作較少，但 pipeline 仍須先查一輪才拿得到 id，
  且與既有原則相斜，捨棄
- **id 定位保留**：既有端點、測試與 Insomnia 請求不需改寫；兩者同時提供時以 id 為準

### D2：自然鍵解析集中在一處，不散在各 service

八類資料各有不同的自然鍵組合，若解析邏輯分散，日後新增內容表時容易漏。

- **採用**：在 `service/review` 下建立單一解析元件，依 `ReviewTargetType` 分派到對應 repository 查詢
- **回傳語意**：查無資料回 404、自然鍵欄位不足回 400 且訊息指出缺哪些維度——
  後者對市佔率特別重要，它的自然鍵有六個欄位，少一個就定位不到

### D3：批次建立的回應必須自帶定位資訊

F4 的痛點不是「不能批次」，而是**建立與審核之間斷了一截**：建完要自己收集 id 才能審核。

- **採用**：批次建立回應的每筆成功項目帶自然鍵（與 D1 同一組），呼叫端可直接把回應轉成批次審核請求
- **驗收標準寫進 spec**：「建立後直接批次審核，過程中不需額外查詢」——
  這是可測的行為，不是模糊的易用性宣稱
- **失敗項目不帶定位資訊**：避免呼叫端誤以為建立成功

### D4：公司對外識別由單一組裝邏輯產出

F2 的兩個值都能餵進 `GET /api/companies/{code}`（`getByReference` 會退回名稱查詢），
所以流程不會斷——但同一家公司在兩個回應裡叫不同名字，呼叫端很難不誤會，
AI pipeline 更會因此把同一家公司當成兩個。

- **採用**：抽出共用的公司對外識別組裝：優先主要識別碼代號，無識別碼才退回正規化名稱
- **spec 加一條可測的驗收**：任一回應取出的對外識別，拿去查詢都查得到該公司
- **這是行為變更**：`SupplierResponse.companyReference` 對有代號的公司會從名稱改為代號，
  需在 CHANGELOG 記錄

## Risks / Trade-offs

- **兩種定位方式並存增加測試面** → 以「同時提供時以 id 為準」「兩者皆無回 400」兩條
  scenario 把交互情況釘死，不留模糊地帶
- **自然鍵較長且易填錯**（市佔率要六個欄位） → 400 訊息必須指出缺少哪些維度，
  否則呼叫端只能猜；這條寫進 spec 而非只寫在程式碼
- **批次端點可能被用來一次送出過大批量** → 本次不設上限，但需在 review 時確認
  是否要加筆數上限；AI pipeline 上線前應補
- **F2 是行為變更** → 既有呼叫端若把 `companyReference` 當顯示名稱用會看到代號；
  目前無外部呼叫端，成本可接受

## Migration Plan

1. 無 schema 變更，不需 Flyway migration
2. 先擴充審核端點（自然鍵），再做批次建立——後者的回應格式依賴前者定義的自然鍵型別
3. 既有 id 定位路徑全程保持可用，既有測試不需改寫即應繼續通過
4. 回滾：純 API 層變更，無資料轉換，直接還原程式碼即可

## Open Questions

  待該 change 規劃時才有依據，本次先不設
- 組成關係的 GET 端點路徑放在 `/api/items/{id}/compositions` 或獨立於 `/api/compositions`——
  前者符合既有巢狀風格，後者在跨節點查詢時較直覺；本次採前者，待實際使用再議
