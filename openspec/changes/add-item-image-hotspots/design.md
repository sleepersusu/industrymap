## Context

至今為止的模型是純粹的資料關係，沒有任何呈現層概念——這是刻意的分層，不是疏漏。
本次第一次引入「圖」這個維度，因此真正要決定的不是欄位怎麼開，而是
**圖與既有品類模型的接合點放在哪**：放錯地方會污染 `item_composition` 的語意，
而那張表是整個地圖的骨架。

既有的兩個約束決定了大部分答案：節點是**品類**不是型號（core model design D2），
組成關係的唯一鍵是 `(parent_item_id, child_item_id)`（無數量、無位置）。

## Goals / Non-Goals

**Goals:**
- 前端能以一次呼叫取得一張爆炸圖的全部熱區，並在點擊後下鑽到該品類的供應公司
- 同一張圖上多個位置指向同一個品類節點（前／後煞車）時，彼此可區分
- 兩張新表與既有的來源、審核、批次建立機制完全一致，不長出第二套規矩

**Non-Goals:**
- 不做圖片上傳（見 D4）
- 不做熱區編輯器 UI（本次只到 API；座標暫由人工量測或外部工具產生，見 Risks）
- 不引入具體車款組態層（見 D1）
- 不改 `item_composition` 的唯一鍵、欄位或語意（見 D2）

## Decisions

### D1：熱區指向品類節點，不引入具體車款組態層

兩種語意：

| 方案 | 點擊變速器得到的答案 | 代價 |
|---|---|---|
| **熱區指品類（採用）** | 「做變速器的公司有這些」 | 一張圖代表一個品類的通用拆解，不分車款 |
| 熱區指具體型號 | 「這台車的變速器是 Shimano」 | 需逐車款建 BOM，資料量與維護成本量級躍升 |

選前者，三個理由：

1. **爆炸圖天生是示意圖**。它是拆解圖解而非產品實拍，本來就是品類層級的表達，
   與現有模型語意相符；後者反而要為每個型號找到對應的實拍分解圖。
2. **資料成本是量級差異**。品類拆解一台車幾十個節點可人工建；具體 BOM 要逐型號查、
   且隨年份改版過期。專案連情資層都還沒接。
3. **不擋後路**。日後真要做具體組態，`item_image` 再加一個可選的組態維度即可，
   熱區與座標資料完全可沿用。

`goal.md` 寫的目標本來就是前者（「這台腳踏車的零件分別來自哪些公司」是品類層級的答案）。

### D2：位置標籤放在熱區，`item_composition` 一個字都不改

前煞車與後煞車在組成關係上是同一條邊（`UNIQUE (parent_item_id, child_item_id)`），
但在圖上是兩個熱區。三種解法：

| 解法 | 結果 |
|---|---|
| 給 `item_composition` 加數量／位置、改唯一鍵 | 連帶影響審核端點、自然鍵、批次建立與所有既有查詢 |
| 熱區只存 `child_item_id` | 兩個熱區資料完全相同，前端無從區分——等於沒解決 |
| **熱區自帶位置標籤（採用）** | `item_composition` 不動，兩個熱區以標籤區分 |

判準是**這個事實屬於誰**：「腳踏車有煞車」是組成關係的事實，不因車上有兩個煞車而變成兩筆；
「這張圖的左下角那塊是前煞車」是圖的事實。位置只在畫圖時才需要存在，
把它塞進 `item_composition` 是讓骨架去承擔呈現層的責任。

改唯一鍵的代價與收益也完全不成比例：`(parent, child)` 這組鍵是既有自然鍵定位的一部分，
動它等於動 `NaturalKeyResolver`、審核端點契約與所有既有測試，只為了畫圖。

### D3：自然鍵是「節點 + 視角標籤 + 位置標籤」，全程不需內部 id

- **圖片**：`(item_id, view_label)`——一個節點的「爆炸圖」「側視圖」各一張
- **熱區**：`(item_image_id, position_label)`——一張圖上的「前煞車」只有一個

位置標籤 MUST 非空。若允許為 null，PostgreSQL 的 `UNIQUE` 視 NULL 互不相等，
唯一鍵形同虛設，同一張圖可以塞進無限多筆指向同一節點的熱區。強制命名的代價很小
（單一煞車就叫「煞車」），換來的是唯一鍵真的守得住。

對外的自然鍵因此是「節點名稱 + 視角標籤 + 位置標籤」，呼叫端全程不需要知道任何內部 id——
與既有八類一致。組成關係的自然鍵用的是節點 id（`parentItemId` + `childItemId`），
這裡沿用同樣的寬容度：兩種定位方式都接受，同時提供時以 id 為準。

**注意唯一鍵不含 `child_item_id`**：同一張圖上兩個位置標籤不同的熱區可以指向同一個節點
（這正是 D2 要解的問題），而同一個位置標籤不該同時是煞車又是變速器。

### D4：只存物件儲存的 key／URL，二進位不進資料庫，本次不做上傳

理由不只是「DB 會變大」：圖片進 DB 之後備份與還原時間跟著膨脹、JPA 讀取一個節點會
順手把 blob 拉進記憶體、CDN 也無法直接服務。這些代價全部沒有對應收益。

上傳端點刻意排除在本次之外——它牽涉物件儲存的選型、簽章 URL、檔案大小與型別驗證，
是一個獨立的問題。本次先接受外部已存在的 URL，讓資料層與讀取路徑先跑通。

### D5：座標用 0–1 相對比例的多邊形點集

- **相對比例**：圖片在手機縮到 375px 寬時熱區仍對得準；存絕對像素等於把熱區綁死在
  某一次的圖片解析度上，換圖或換裝置就全歪
- **多邊形而非矩形**：矩形是多邊形的特例，一開始就用多邊形不會後悔；
  零件形狀本來就不是方的，用矩形會讓相鄰熱區互相重疊
- **至少三點**，每個座標值落在 `[0, 1]`

以 JSONB 儲存。`.claude/rules/code-style.md` 的既有地雷在此適用：
以 `@Type(JsonType.class)` 持久化自訂 POJO 時，**物件圖每一層都要 `implements Serializable`**
（且依慣例不加 `serialVersionUID`），否則 Hibernate dirty-check 的 deep-clone 會直接拋
`JpaSystemException`。座標點的 POJO 必須實作它。

驗證能用 `jakarta.validation` 表達的一律用 annotation（點數下限、座標範圍），
但 service 層需再擋一次：日後 AI 拆解流程會繞過 HTTP 直接呼叫 service 寫入，
只靠 payload annotation 那條路徑就守不到。

### D6：讀取端點回巢狀結構，一次呼叫拿完一張圖

`GET /api/items/{id}/images` 回圖片清單，每張圖帶自己的熱區陣列。

不拆成 `/images` 與 `/images/{id}/hotspots` 兩個端點：前端要畫出一張可互動的圖，
圖與熱區缺一不可，拆開必然變成「先拿圖、再逐張拿熱區」的 N+1，只是把問題從後端搬到前端。
巢狀深度仍在既有規則的兩層之內。

查詢條件收斂成 `ItemImageQuery`（`includeDrafts`），與既有 GET 端點一致。

### D7：熱區的移除以審核駁回表達，不做實體刪除

畫錯的熱區需要能拿掉，但專案已經有這個機制：審核狀態轉為 REJECTED 後，該筆即不再出現在
任何對外查詢。再開一個 `DELETE` 等於對同一件事給出第二種作法，且會失去「誰在何時拿掉的」
這段軌跡——而軌跡正是整套 provenance 存在的理由。

座標畫歪（而非畫錯對象）則走 `PUT` 全量替換，沿用既有的「內容變更後審核狀態退回草稿」語意。

### D8：審核可見性——新端點觸及四張內容表

| 表 | 層次 | 判定 |
|---|---|---|
| `item`（路徑上的節點） | 主查詢 | **實體** → 只擋 REJECTED（`exposableStatusNames`） |
| `item_image` | 主查詢 | **關係**（「這個節點有這張圖」）→ 跟 `includeDrafts` 走 |
| `item_hotspot` | join | **關係**（「這塊區域是這個零件」）→ 跟 `includeDrafts` 走 |
| `item`（熱區指向的節點） | **關係指向的實體** | **實體** → 只擋 REJECTED |

第四格是 `.claude/rules/architecture.md` 明載「最常漏」的那一格，且同一個模式在本專案
已經漏過三次。熱區已驗證不代表它指向的品類節點還算數——節點事後被駁回時，
該熱區 MUST NOT 出現，否則使用者點下去會下鑽到一個不該存在的節點。

四格全部登記進 `ReviewVisibilityMatrixTest` 並各配一支斷言。

### D9：查詢筆數——熱區指向的節點必須 join fetch

回應要讀每個熱區指向節點的名稱與審核狀態，`childItem` 是 LAZY 關聯；
`Item` 的 `@Id` 標在欄位上，Hibernate 連讀主鍵都會觸發代理初始化，所以不 join fetch
就是逐筆 N+1。repository 查詢加 `@EntityGraph(attributePaths = "childItem")`。

`QueryFanoutTest` 加一格，**大扇出設在 60**（`default_batch_fetch_size` 為 50）。
兩種扇出都低於批次值時，批次抓取會把兩者壓成一次 `IN` 查詢，於是「筆數相同」在
有沒有 `@EntityGraph` 都成立——守衛全綠卻什麼也沒守。這個洞上一個 change 已實測踩過。

## Risks / Trade-offs

- **座標怎麼產出**：本次只做 API，沒有編輯器。在編輯器做出來之前，座標得靠人工量測或
  外部工具（影像標註軟體匯出）產生，作業體感不會好。接受，理由是編輯器是前端工作，
  而它需要這組 API 先存在；反過來做不成立
- **一個品類只有一張通用爆炸圖**（D1 的直接後果）：不同車款外觀差異大時，
  圖與實物對不太起來。這是示意圖語意的固有限制，不是 bug；真的成為問題時走 D1 說的
  組態維度擴充路徑
- **位置標籤是自由文字**，「前煞車」與「前輪煞車」會被視為兩個不同的位置。
  不引入位置的受控字彙表——那是另一套正規化機制，在只有幾十筆熱區時成本高於收益。
  日後真的亂掉時再收斂
- **JSONB 座標無法用 DB constraint 驗證**：點數與範圍只能靠 annotation 與 service 擋。
  繞過 service 直接寫 DB 就會失效——與既有的循環偵測、別名去重是同一類已知取捨
