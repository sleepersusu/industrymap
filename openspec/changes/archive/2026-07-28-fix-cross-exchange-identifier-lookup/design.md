## Context

`CompanyReferences.of` 產出的對外識別是主要識別碼的**裸代號值**，`CompanyService.getByReference`
反過來以該值查回公司。兩邊都不看 `identifierType`，而唯一鍵是 `(identifier_type, identifier_value)`——
也就是說系統的對外識別建立在一個**不保證唯一**的欄位上。

前一支 change（`add-exchange-identifier-types`，已歸檔）把 `OTHER` / `HKEX:6088` 這種畸形值
轉成 `HKEX` / `6088`，並補上六個交易所類型。那是正確的修正，但它移除了先前無意間扮演命名空間角色的前綴，
讓這個既有缺陷從潛伏變成可觸發。目前資料庫裡尚無重複值，因此還沒有實際故障。

相關程式：`helper/CompanyReferences`（組裝規則唯一來源，design D4 訂下）、
`service/company/CompanyService:151-175`（解析）、`:230-260`（產出）、
`repository/CompanyIdentifierRepository.findByIdentifierValue`。

## Goals / Non-Goals

**Goals:**
- 讓對外識別**永遠唯一且可反查**——拿到任一回應中的識別值，查回來一定是同一家公司
- 讓識別值**穩定**：不因為別人新增了一筆無關資料而改變既有公司的識別值
- 撞號時給出明確錯誤與可行動的候選，而不是靜默選一筆

**Non-Goals:**
- 不改 `unique(type, value)`，也不禁止不同交易所使用相同代號值——那是現實而非錯誤
- 不做識別碼的修正端點
- 不改變未上市公司以正規化名稱作為識別的既有設計
- 不做「依交易所查詢公司列表」這類新查詢能力

## Decisions

### D1：對外識別改為 `<類型>:<代號值>` 的限定形式

- **採用**：`TWSE:2330`、`HKEX:6088`、`TAX_ID:12345678`。公司路徑同步變成 `/api/companies/TWSE:2330`
- **理由**：代號的命名空間就是交易所，識別值必須把命名空間帶上才可能唯一。
  `(type, value)` 是資料庫唯一鍵，限定形式是它的字串投影，兩者一一對應
- **替代方案 A：只在有歧義時才帶類型**（平時仍是 `2330`）——否決。識別值會因為第三方
  新增一筆 `SSE 2330` 而從 `2330` 變成 `TWSE:2330`，把別人存下的舊值弄壞。
  「識別值的形狀取決於別處有沒有撞號」是很難除錯的耦合
- **替代方案 B：改用正規化名稱當對外識別**——否決。`normalized_name` 確實天然唯一，
  但代號是公司最自然的對外識別（design D5 的原始意圖），且名稱改動比代號頻繁
- **替代方案 C：只修解析端、識別值不動**——否決。撞號時那兩家公司的識別值實質不可用，
  等於做出「資料進得去、出不來」的類型，正是 `.claude/rules/api-design.md` 明令避免的

### D2：這**不是**回到 `HKEX:6088` 的老路——儲存與呈現是兩層

前一支 change 才剛把 `HKEX:6088` 從**值**裡拔掉，這裡又讓 `HKEX:6088` 出現在對外識別上，
表面看像繞回原地。兩者的差別必須寫清楚，否則下一個人會以為我們反覆橫跳：

| | 前一支 change 移除的 | 本 change 加入的 |
|---|---|---|
| 位置 | `identifier_value` 欄位（落地） | 回應欄位與路徑參數（投影） |
| 後果 | 唯一鍵語意被稀釋、無法依交易所查詢、格式全靠人工約定 | 唯一鍵不受影響；形狀由程式產生，不靠人工約定 |

**判準**：交易所資訊在**儲存層**必須是獨立欄位（才能下 constraint、才能依交易所查詢）；
在**識別層**必須與代號綁在一起（否則識別值不唯一）。兩者不衝突，前者是後者的資料來源。

### D3：解析規則——含冒號才當限定形式，且前綴必須是合法類型

`getByReference` 收到的字串有三種可能：限定形式、裸代號、公司名稱。判別順序：

1. **含冒號且冒號前是合法的 `IdentifierType` 名稱** → 限定形式，以 `(類型, 值)` 查唯一鍵
2. 否則 → 沿用現行順序：先當裸代號查，查不到再當公司名稱查

- **為什麼「前綴必須是合法類型」這個條件不可省**：識別碼值本身可能含冒號
  （`OTHER` 底下合法的 `ISIN:DE0006231004` 之類），少了這個條件會被誤判成限定形式而查無資料
- **為什麼公司名稱不會被誤判**：`NameNormalizer` 移除所有標點（`\p{P}`），
  `normalized_name` 不可能含冒號，因此含冒號的輸入絕不會是名稱
- **裸代號仍支援**：手冊與既有操作大量使用裸代號，全面斷掉沒有好處。
  但單筆命中才回傳，多筆命中回 409

### D4：裸代號多筆命中回 409 而非 404 或任選

- **409 Conflict**，訊息須列出所有候選的限定形式，呼叫端可直接挑一個重送
- 不用 404：資料是存在的，問題是輸入不足以指定唯一一筆
- 不用「取主要識別碼優先」這類消歧義規則：兩家公司都可能以該代號作為主要識別碼，
  規則救不了真正的歧義，只會讓錯誤更難察覺

### D5：組裝規則仍然只有一份

`CompanyReferences` 是 design D4 訂下的唯一組裝點，本 change 只改它的輸出形狀，不新增第二套規則。
解析端需要的「限定形式 → (類型, 值)」拆解與它成對，一併放在同一個 helper，避免組裝與拆解各寫一份而漂移。

## Risks / Trade-offs

- **破壞性變更，所有回應的識別值與公司路徑都變** → 目前無外部呼叫端，
  `docs/data-loading-playbook.md` 是唯一需要同步的操作文件。越晚改成本越高，現在改最便宜
- **識別值變長、可讀性略降**（`TWSE:2330` vs `2330`） → 換來的是唯一與穩定。
  對人的可讀性其實提升：光看值就知道是哪個市場
- **冒號在 URL path segment 中合法**（RFC 3986 的 `pchar` 含 `:`），不需 encode；
  但仍須以實際請求驗證 Spring 的路徑變數綁定，不能只靠推論
- **既有測試大量使用裸代號斷言** → 屬預期範圍內的同步成本，依 `.claude/rules/testing.md`
  先搜尋所有引用再改，避免 `test-compile` 中斷
- **本 change 修正的是「還沒發生的故障」** → 撞號目前無實例，因此驗收必須靠
  刻意建構的撞號資料，不能等真實資料出現

## Migration Plan

1. 先做 helper 的組裝與拆解（純函式，無 DB），連同解析規則的單元測試
2. 再改 repository 與 `CompanyService` 的解析與產出
3. 最後同步既有測試與 `docs/data-loading-playbook.md`
4. 無 schema 變更、無 Flyway migration；回滾即還原程式碼，不需要資料處理
