## Context

`add-natural-key-review-and-batch-write` 完成後，寫入與審核的閉環已通，
於是 2026-07-27 / 07-28 用它灌了主機板：22 個節點、28 家公司、42 筆供應角色，全部 `VERIFIED`。
灌完才發現閉環少的不是寫入端，是**讀取端與修正端**：

- 資料在資料庫裡，但沒有任何 API 能列出「有哪些成品可以點」——
  前端首頁無從開始，連我自己驗證都得靠 `psql`
- `主機板` 被建成終端成品且無上層。這個判斷本身可以爭論（架構文件與手冊都拿它當終端成品範例），
  但**爭不爭得出結論不重要，重要的是現在改不掉**

本 change 只處理品類節點這條線。公司雖有同樣的缺口，但沒有實際卡點，
留到有需求時再做，避免一次改動面積過大。

## Goals / Non-Goals

**Goals:**
- 讓呼叫端在不知道任何 id、不查資料庫的前提下，取得可進入的終端成品清單
- 讓建錯的節點欄位可以修正，且修正走的是與建立同一組的跨表檢查
- 讓已驗證的資料無法被靜默改寫

**Non-Goals:**
- **不做「列出所有節點（含零件）」**。第八節 G1 的另一半——灌資料前撈既有清單當 background——
  在本 change 後**仍需直接查資料庫**。理由見 D1；遷移路徑一併記在該節
- 不做公司的列表與修正端點
- 不做覆蓋度過濾（G5）
- 不做刪除節點。錯誤資料的既有處理方式是審核為 `REJECTED`（資料保留，不外露），
  本 change 不改變這個做法
- 不做前端與權限控管

## Decisions

### D1：列表掛 `/api/products` 且只列終端成品，不動 `/api/items`

三條路都試著推演過：

- **方案 A（採用）**：新增 `GET /api/products` 列終端成品。
  `/api/products` 在本專案的既有語意就是「以某節點為根看樹」（`/api/products/{id}/components`
  接受任何 `Item` 的 id），因此「列出可以當根來看的節點」語意連貫。
  `GET /api/items?name=` 完全不動。
- **方案 B（捨棄）**：讓 `GET /api/items` 兼做列表。致命問題是**回應形狀會隨參數改變**——
  帶 `name` 回單一物件、不帶回陣列。這種契約對呼叫端最不友善，尤其 AI pipeline 會直接誤判。
- **方案 C（捨棄，但保留為未來路徑）**：把單筆解析移到 `GET /api/items/resolve?name=`，
  讓 `GET /api/items` 變成純列表。契約最乾淨，但這是 breaking change：
  手冊紀律 1 的第二道防線指令、灌資料腳本、既有測試都要改。
  目前沒有外部呼叫端，成本不是不能付，但**本次的痛點是「首頁點不進來」，
  用不到列零件**，為此付 breaking change 的代價不划算。

**代價要講清楚**：方案 A 讓 G1 只解一半。灌資料前撈既有節點清單（含零件）當 background 去重，
本 change 後仍得走 `psql` 唯讀查詢。這是刻意的取捨，不是遺漏。
日後真要列零件時，走方案 C 的遷移路徑：先加 `/api/items/resolve`、
兩者並存一段時間、更新手冊與腳本後再讓 `/api/items` 轉為列表。

### D2：修正用 PUT 全量替換，不用 PATCH

- **決定性理由**：`endProduct` 是布林值。PATCH 的語意是「只改有送的欄位」，
  但 JSON 反序列化後**無法區分「沒送 endProduct」與「送了 endProduct: false」**——
  用包裝型別 `Boolean` 加 null 判斷可以解，但那讓「把終端成品改成非終端成品」
  這個本 change 最主要的用例，取決於呼叫端有沒有正確理解 null 的三態語意。太脆。
- **次要理由**：`parentCategoryId` 需要能被清空。PATCH 下 null 同樣有「不改」與「清空」的歧義。
- **採用**：`PUT /api/items/{id}`，request body 必須帶齊 `displayName`、`endProduct`、
  `parentCategoryId`（後者可為 null 表示無上層品類）。缺欄位回 400。
- **代價**：呼叫端要先查一次現值。修正是低頻的內部作業，且 `GET /api/items/{id}` 已存在，
  這個成本可以接受。

### D3：實際變更才退回 DRAFT，無變更的重送不動狀態

使用者已定調「改內容就退回 DRAFT」——對外資料都經過審核這條線，優先於便利性。
但這條規則有一個必須釘死的邊界：

- **值真的改變**（正規化後比較 `displayName`，直接比較 `endProduct` 與 `parentCategoryId`）
  → 審核狀態一律設為 `DRAFT`，該節點立刻從對外查詢消失，需重新審核
- **送進來的值與現值完全相同** → **不改狀態**。否則「重送一次相同內容」
  會讓一筆已驗證資料無故從對外查詢消失，而呼叫端什麼都沒改。
  批次流程重跑、前端重複送出都會踩到這個
- **已 `REJECTED` 的節點修正後同樣轉為 `DRAFT`**，讓它有重新來過的機會——
  否則駁回等於永久死刑，而駁回的原意是「這筆有問題」不是「這個節點不該存在」

**代價**（寫進 Risks）：改一個錯字也會讓資料暫時從對外查詢消失。這是使用者知情下的選擇。

### D4：名稱衝突檢查抽成共用，三處呼叫同一份

`ItemService` 現在有兩處各自實作了部分規則：
`create` 檢查 `existsByNormalizedName`；`addAlias` 檢查「別名撞到其他節點的名稱」與「別名已被登記」。
改名需要的是這兩者的聯集，若再寫第三份，三處規則遲早漂移。

- **採用**：抽出單一檢查方法，輸入是「正規化名稱 + 要排除的節點 id」，
  輸出是衝突與否及原因。`create`（排除 id 為空）、`addAlias`、改名共用
- **改名要擋的完整條件**：新正規化名稱不得等於**其他節點**的正規化名稱，
  也不得等於**任何已登記別名**（包含該節點自己的別名——否則
  `item.normalized_name` 與自己的 alias 重複，資料重複且無意義）

### D5：is-a 上層的循環要自己擋，不能沿用 part-of 的循環偵測

`ItemCompositionService` 已有循環偵測，但守的是 `item_composition`（part-of，多對多 DAG）。
`parentCategoryId` 是 `item` 表上的自我 FK（is-a，至多一個上層），是另一條關係，
兩者刻意分離（既有 design D4）。因此：

- **採用**：在 `ItemService` 內對 is-a 鏈做上溯檢查，擋掉自我指向與 A→B→A 這類循環
- **不共用** `ItemCompositionService` 的偵測邏輯——關係不同、資料表不同，
  硬共用只會讓兩邊都變難懂

### D6：列表的排序必須穩定，否則分頁會漏資料

- 預設依 `display_name` 排序（給人看的清單），**並固定以 `id` 作為 tie-break**。
  正規化名稱是唯一鍵，因此完全相同的 `display_name` 進不來；但排序用的是 `display_name` 本身，
  在資料庫定序規則下可能有「不同字串但比較結果相等」的情況（大小寫、全形半形、
  Unicode 正規化差異），此時排序順序不保證穩定，分頁會在頁與頁之間漏或重複資料。
  加上 `id` 作為第二排序鍵就能釘死，成本是零
- 分頁參數與過濾條件依 `.claude/rules/architecture.md` 收斂成 `*Query` payload，
  以 `@Valid @ModelAttribute` 綁定，不逐個接 `@RequestParam`
- 需要新增分頁回應 payload（專案目前沒有）。回應需含 content、頁碼、每頁筆數、
  總筆數與總頁數——總筆數是前端顯示「共 N 項」的必要資訊

### D7：草稿與駁回的曝露規則沿用既有慣例，不新發明

- 預設只回可曝露狀態（`VERIFIED`）
- 明確指定納入草稿時（沿用 `ComponentTreeQuery` 既有的 `includeDrafts` 參數名）才含 `DRAFT`
- **`REJECTED` 任何情況都不外露**，與既有 `ReviewScopes` 一致

## Risks / Trade-offs

- **G1 只解一半** → 已在 Non-Goals 明確記錄，並留下方案 C 的遷移路徑。
  手冊第八節 G1 需改寫，說明剩餘範圍仍走資料庫唯讀查詢，避免下一輪的人以為有列表可用
- **改錯字會讓資料暫時消失於對外查詢**（D3） → 使用者知情下的選擇。
  若日後發現修正頻繁而審核跟不上，再考慮「僅顯示欄位不退回」的分級規則
  （這是當時被評估過但因規則變複雜而未採用的方案）
- **PUT 全量要求呼叫端先查現值**（D2） → 修正是低頻內部作業，`GET /api/items/{id}` 已存在
- **名稱模糊搜尋用不到既有索引** → `normalized_name` 的唯一索引只支援前綴查詢，
  contains 查詢會走全表掃描。目前節點數是兩位數，不構成問題；
  **本 change 不加索引**，但需在 tasks 中明確記錄這個已知限制，避免日後誤以為評估過了
- **修正端點會動到 `ItemService`** → 依 `.claude/rules/testing.md`，
  必須先搜尋並同步所有引用該類別的既有測試檔，再繼續 TDD，否則 `test-compile` 會斷

## Migration Plan

1. **無 schema 變更，不需 Flyway migration**——本 change 只加端點與查詢，
   不動資料表、欄位、索引與約束。tasks 中明確確認一次，不靠「應該不用」帶過
2. 先做列表端點（唯讀、風險低、直接解掉首頁點不進來的問題），再做修正端點
   （會動既有 service 與既有測試）
3. 修正端點完成後，可用它把 `主機板`（id 241）的 `endProduct` 調整為正確值——
   但「主機板到底算不算終端成品」是資料決策，不在本 change 範圍，
   本 change 只負責讓它**改得動**
