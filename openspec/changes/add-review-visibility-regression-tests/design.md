## Context

三次遺漏的共同形狀是「新增查詢路徑時，沒把某張可觸及的內容表的 `review_status` 納入」。
值得注意的是三次漏的**層次不同**：

| 次序 | 漏掉的層次 | 位置 |
|---|---|---|
| 1 | 主查詢表自身 | 識別碼的 `review_status` |
| 2 | join / 子查詢的表 | 別名的 `review_status` |
| 3 | 關係**指向**的實體 | 供應角色指向的品類節點 |

第 3 種最不直覺，也最晚被抓到。任何有效的測試設計都必須同時覆蓋這三個層次，
只測「主表的已駁回資料查不到」會完全漏掉第 2、3 種。

現況資產：`AbstractPostgresIntegrationTest`（真實 PostgreSQL + Flyway）、`FIXTURE_PREFIX`
（共用開發資料庫下的 fixture 隔離）、`ReviewScopes`。8 張內容表、10 個 GET 端點。

## Goals / Non-Goals

**Goals:**
- 每個對外 GET 端點 × 每張它可觸及的內容表，都有一格「已駁回不外露」的驗證
- 覆蓋三個層次：主表、join 表、關係指向的實體
- **新增端點若未登記進矩陣，build 必須紅**——這是本次真正的價值所在

**Non-Goals:**
- 不驗證 `includeDrafts` 的草稿語意。各端點對草稿的取捨不同（`ReviewScopes` 明確區分關係與實體），
  混進來會讓這組測試變成規格重述而非防呆，且草稿語意本來就該由各端點自己的測試守
- 不改動既有端點行為。測試若揭露不一致，逐項判斷後另案處理（見 Risks）
- 不做 hook。hook 只能提示不能判斷「這裡確實不需要過濾」，價值低於會紅的測試

## Decisions

### D1：以「端點 × 內容表」矩陣驅動，集中在單一測試類別

每格斷言：在該表塞一筆 REJECTED 的 fixture，呼叫該端點，該筆資料及其影響**都不得出現**。

- **理由**：三次遺漏都不是單一端點的問題，而是「這條規則沒有統一的執行點」。
  散在各端點的測試正是現況，已證明會漏
- **「不得出現」有兩種形狀**，兩種都要涵蓋：
  - **直接外露**：已駁回的資料本身出現在回應中（例：已駁回識別碼被列進公司回應）
  - **間接影響**：已駁回的資料改變了結果（例：已駁回別名讓公司被搜到、
    已駁回識別碼讓合法查詢回 409、已駁回節點讓公司出現在角色清單）
    ——三次實際缺陷有兩次屬於這一種，只測直接外露會全部漏掉

### D2：加一道覆蓋率守衛，未登記的端點讓 build 紅

測試自 Spring 的 `RequestMappingHandlerMapping` 取出所有 GET 端點，
與矩陣中登記的端點集合比對；有端點未登記即 fail，訊息指向本規則。

- **理由**：這是唯一能擋住**未來**遺漏的機制。矩陣本身只覆蓋今天已知的 10 個端點，
  沒有這道守衛，明天新增的第 11 個端點依然會靜默漏掉——那正是這三次的發生方式
- **刻意不自動推導「該端點會碰哪些表」**：靜態分析 native SQL 不可靠，
  推導錯會產生假警報而讓人開始忽略這支測試。改為**人工登記、機器強制登記這件事本身**
- **登記為空要能通過但需明示**：確有端點不觸及任何內容表時，登記為「無」並附理由，
  不得省略登記

### D3：fixture 一律走 `FIXTURE_PREFIX` 並限定斷言範圍

沒有 Docker 時整合測試跑在共用開發資料庫上，整張表已有真實資料。
斷言一律限定在本測試自建的 fixture 上，不對全表數字下斷言（沿用既有慣例）。

### D4：測試命名與失敗訊息直接指向規則

失敗訊息須寫明「哪個端點、哪張表、漏了哪個層次的過濾」，並引用
`.claude/rules/architecture.md` 的五問清單。測試紅掉時人要能立刻知道該做什麼，
而不是先花時間讀測試程式碼。

## Risks / Trade-offs

- **預期會揭露既有的不一致** → 已知至少一處：指名一個**已駁回的品類節點**時，
  `GET /api/products/{id}/components` 回傳該節點，而 `GET /api/companies?itemId=` 回空清單。
  兩者都說得通但不一致。本次**不預設結論**：測試寫出來後逐項判斷是修程式還是修預期，
  若屬設計決策則另開 change，不在本次夾帶行為變更
- **矩陣需人工維護** → D2 的守衛只能強制「有登記」，不能強制「登記正確」。
  一個端點若被登記成「不觸及任何表」而實際上會碰，守衛抓不到。
  這是刻意的取捨：機器判斷不了的部分不假裝能判斷，但至少讓遺漏從「靜默」變成「要主動說謊」
- **測試數量與執行時間** → 10 端點 × 平均 2–3 張可觸及的表，約 20–30 格。
  全部走真實 PostgreSQL，屬 `integration` 軌，不影響日常快測迴圈
- **過度斷言的風險** → 每格只斷言「該筆已駁回資料及其影響不出現」，
  不順便斷言回應的其他內容；否則端點一改動這組測試就整批紅，變成維護負擔而被停用
