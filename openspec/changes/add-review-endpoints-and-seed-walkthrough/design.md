## Context

八張內容表共用 `ProvenanceEntity`（`@MappedSuperclass`），`ReviewService.applyReview()` 以泛型
實作審核狀態流轉，已通過 6 個單元測試。缺的只是對外介面。

同時整套 API 從未被實際使用過——所有測試都是單元測試與 repository 整合測試，
沒有任何一次「先建 A、再用 A 的 id 建 B」的真實串接。這是本次要補的第二件事。

## Goals / Non-Goals

**Goals:**
- 讓草稿資料能轉為已驗證，打通「資料進得去也出得來」的閉環
- 審核介面能承受未來 AI 一次生成數百筆的量，不是只為手動點選設計
- 以最小規模的真實資料端到端驗證核心查詢，並記錄 API 用起來哪裡不順

**Non-Goals:**
- 不做審核的前端介面（本次只到 API）
- 不做審核歷程記錄（誰在什麼時候把它從 A 改成 B 的完整軌跡），目前只保留最後一次
- 不做權限控管（誰有資格審核），目前審核者是呼叫端自行填入的字串
- 種子資料不進 Flyway migration，不成為專案的預設資料

## Decisions

### D1：統一審核端點，而非各資源底下分散的端點

- **採用**：單一 `ReviewController`，請求帶「資料類型 + 識別碼 + 目標狀態 + 審核者」
- **理由**：審核邏輯在 `ReviewService` 只有一份，八張表行為完全一致；分散成八組端點會產生
  八份幾乎相同的樣板，且日後新增內容表就要再補一組。更關鍵的是批次審核天生跨類型
  （建完一台腳踏車後，要一次審掉節點、關係、公司、市佔率），分散端點做不到
- **替代方案**：`PATCH /api/items/{id}/review`、`PATCH /api/companies/{code}/review`⋯ →
  較符合資源導向直覺，但無法跨類型批次，且樣板重複，捨棄
- **代價**：這是「以類型參數驅動」的通用端點，型別安全較弱。以 enum 白名單限制可接受的類型，
  不在清單內回 400 而非 500（見 spec 對應 scenario）

### D2：批次採逐筆回報，不整批 rollback

- **採用**：批次中個別失敗不影響其他項目，回應逐筆帶成功／失敗與原因
- **理由**：審核的語意是「人看過後蓋章」。一筆識別碼打錯不該讓另外 99 筆已經看過的資料白審。
  未來 AI 一次生成數百筆時，全有全無會讓整批反覆重送
- **替代方案**：全有全無（單一交易）→ 實作與回應格式都更簡單，對本次 20 筆種子資料也夠用，
  但改成逐筆回報屬於破壞性的回應格式變更，寧可一次到位
- **交易邊界**：每筆審核各自為一個交易，不共用；避免長交易持有連線

### D3：種子資料走真實 API，不寫 SQL 也不進 migration

- **採用**：以 Insomnia collection 依序呼叫既有端點建立資料，請求保留在版控中可重跑
- **理由**：直接寫 SQL 會繞過所有 service 層驗證（循環偵測、別名衝突、來源必填），
  等於沒有驗證到任何東西；而本次的目的正是要驗證這些路徑真的能用
- **不進 Flyway migration**：種子是驗證用的範例資料，不該成為所有環境的預設內容

### D4：市佔率種子資料必須附真實來源，查不到就不填

- **採用**：`market_share` 的每筆種子資料都要有可查證的 `source_detail`；找不到可靠數字時留空不填
- **理由**：整套模型的價值建立在來源可追溯上（design D8）。若種子資料自己編造百分比，
  等於第一天就示範了錯誤用法，且日後無人分得清哪些是真的
- **`market_share` 允許為空**：核心地圖的三個查詢中，只有市佔率排名依賴它，
  其餘兩個查詢不受影響

### D5：供應關係改以公司代號指定，不曝露公司內部 id

實測發現流程是斷的：`CompanyResponse` 只回 `reference`（代號）而無 `id`，但
`CreateCompanyItemRoleRequest` 與 `CreateMarketShareRequest` 都要求 `companyId`。
建完公司後無從取得 id，只能直接查資料庫才建得了供應關係。

這同時是規則自相矛盾：`.claude/rules/api-design.md` 明定「公司以公司代號作為路徑識別，
不用內部自增 id 曝露於外部 API」，供應關係端點卻要求內部 id。

- **採用**：供應角色與市佔率的寫入改以公司代號（`companyCode`）指定公司，由 service 解析為實體
- **替代方案**：在 `CompanyResponse` 加上 `id` → 做法最省事，但違反自己訂的 API 設計原則，
  且內部主鍵一旦外流就很難收回，捨棄
- **零件維持用 id**：`item` 沒有對外代號這種天然識別，`ItemResponse` 本來就回 `id`，維持現狀

### D6：壓測用假資料的紀律

本次種子資料一律用真實內容（見 D3、D4）。但日後若要做效能測試（例如數百節點的組成樹展開），
產生假資料是合理的，須遵守：

- **優先跑在 Testcontainer 內**：容器用完即銷毀，不存在「忘記清掉」的風險
- 若必須寫入開發資料庫：`source_type` 標 `MANUAL`、`source_detail` 明確寫「效能測試用，非真實資料」
- **保持 `DRAFT` 不轉 `VERIFIED`**：對外查詢天然看不到，不必依賴人記得清除
- 禁止為了讓畫面好看而編造市佔率數字寫入並轉為已驗證——那會讓假數據混入正式查詢結果，
  且事後無從分辨（見 D4）

## Risks / Trade-offs

- **通用端點的型別安全較弱** → enum 白名單 + 明確 400，並在 OpenAPI 標註支援的類型清單
- **審核者是自由字串，無身分驗證** → 本次刻意不做權限控管；日後接上認證時，
  審核者應改為由登入身分推導而非呼叫端填寫，屆時是破壞性變更，需明確版本規劃
- **無審核歷程** → 目前只保留最後一次審核結果。若日後需要稽核軌跡，
  需另建歷程表，本次不預先設計
- **種子資料手動建立，難以重現** → 以 Insomnia collection 保存請求；
  但節點 id 是自增值，重跑時 id 會變，關係建立需依當次回傳的 id 調整。
  本次接受此限制，若之後頻繁重建再考慮以名稱解析取代 id

### D7：已駁回的過濾分兩層——關係走 `ReviewScopes`，實體另擋

`/code-review` 揭露的缺口：`ReviewScopes` 原本只套在三張關係表（組成、供應角色、市佔率）的查詢，
但審核端點上線後 `ITEM` / `COMPANY` / 三張別名識別碼表也能被標為已駁回，
而**沒有任何讀取路徑過濾這些實體自身的審核狀態**。結果是一筆已驗證的組成關係
仍會把事後被駁回的節點帶出來，牴觸 spec 的「已駁回一律不外露」。

- **採用**：新增 `ReviewScopes.isExposable(status)`，於實體層一律擋掉 `REJECTED`；
  組成樹、反向查詢、供應商清單、市佔率排名皆檢查所指向的節點／公司本身
- **只擋 REJECTED，不擋 DRAFT**：草稿的取捨屬各查詢自身的 `includeDrafts` 語意，
  且「建立後立刻查回自己剛建的草稿」是既有且必要的行為，不該因本次改動而斷
- **對外與寫入路徑分開**：`getVisibleById` / `getVisibleByReference` / `findVisibleIdentifiers`
  供對外查詢，`getById` / `getByReference` / `findIdentifiers` 留給寫入流程解析實體。
  合併成一個方法會讓「登記別名到一個已駁回的節點」也一併被擋，那是本次 spec 沒要求的行為變更
- **駁回節點的向上路徑不續走**：節點被駁回代表節點本身不成立，經由它往上回溯的祖先同樣不可信

## Open Questions

- 審核端點的路徑命名（`/api/reviews` 或 `/api/internal/reviews`）——審核屬內部作業，
  日後若要與對外查詢 API 分權，放在 `/api/internal` 下較好切；本次先放 `/api/reviews`，
  待權限控管時再議
- 種子資料走完後若發現「建組成關係必須先知道兩邊 id」太難用，是否要支援以名稱建立關係，
  留待驗證後依實際感受決定

## 實測發現的 API 可用性問題（2026-07-26 種子資料走查）

以下皆為走完一台腳踏車的完整流程後實際踩到的，供下一個 change 取捨：

### F1：組成關係與識別碼建立後，沒有任何端點可以再取得其 id（阻塞審核）

`POST /api/items/{id}/components` 的回應**有**帶 id，但一旦漏存就再也拿不回來——
組成關係沒有 GET 端點，組成樹回應（`ComponentNode`）只給 `itemId` 不給關係本身的 id。
`POST /api/companies/{code}/identifiers` 更嚴重：`CompanyIdentifierResponse` **完全不含 id**，
`GET /api/companies/{code}` 回的識別碼清單同樣不含 id。

審核端點以「類型 + id」定位目標，因此**識別碼這一類目前無法經 API 審核**——
本次是直接查資料庫取 id 才完成的。這是閉環上的實質缺口，不是不便而已。

- 可能方向：(a) 各查詢回應補上該筆資料的 id；(b) 審核端點支援以自然鍵定位
  （識別碼用 `type + value`、組成關係用 `parentItemId + childItemId`）。
  (a) 與「不曝露內部自增 id」的原則衝突，但那條原則講的是**公司的路徑識別**；
  審核是內部作業，兩者未必要套同一把尺——需先釐清該原則的適用範圍。

### F2：`SupplierResponse.companyReference` 與 `CompanyResponse.reference` 語意不一致

`CompanyResponse.reference` 優先給主要代號（桂盟國際 → `5306`），
`SupplierResponse.companyReference` 卻一律給正規化名稱（桂盟國際 → `桂盟國際`）。
兩者都餵得進 `GET /api/companies/{code}`（`getByReference` 會退回名稱查詢），
所以流程不會斷，但同一個概念在兩個回應裡給出不同的值，呼叫端很難不誤會。
建議統一由同一個組裝邏輯產出。

### F3：市佔率種子資料最終留空

依 D4 找不到可查證的公開市佔率數字（搜到的百分比都出自二手部落格，
且引用的研究機構與領域對不上），因此一筆都沒寫。核心地圖的三個查詢中，
只有市佔率排名受影響，回空清單而非 404，行為正確。
若之後要真正驗證排名，需先確定一個可長期引用的市佔率資料來源。

### F4：`ProvenanceRequest` 無法指定審核狀態是刻意的，但批次建立資料時很痛

寫入一律為草稿是正確的設計，但一台腳踏車就產生 30 筆待審資料，
且每筆的 id 得自行從各個建立回應中收集。批次匯入或 AI 生成流程上線前，
應考慮讓建立端點支援批次並在回應中一併回傳所有新資料的 id（供隨後的批次審核使用）。
