# query-performance Specification

## Purpose
管的不是「查得對不對」（那是各能力自己的規格），而是「查一次要打幾次資料庫」。
這條性質會隨資料成長而靜默劣化：資料量小時完全看不出來，等看得出來時已經是線上問題，
而且沒有守衛就不會有人發現它長回來。因此把它獨立成一條能力，
連「守衛本身必須有效」都寫進要求——一個偵測不到退化的驗證，比沒有驗證更糟，
因為它會讓人以為這件事有人在管。
## Requirements

### Requirement: 對外查詢的資料庫往返次數與結果筆數脫鉤

對外查詢端點送出的 SQL 筆數 MUST NOT 隨回傳筆數線性成長。同一支查詢在不同扇出
（回傳筆數）之下，送出的 SQL 筆數 SHALL 相同。

此要求 MUST 有可執行的驗證守住，且該驗證 SHALL 以「兩種扇出的筆數相同」表達，
MUST NOT 以「筆數不得超過某常數」表達——後者會隨無關的實作調整而失敗，
反覆誤報會讓人停用它，於是真的長回線性成長時反而沒人發現。

該驗證的大扇出 MUST 大於批次抓取的設定值。兩種扇出都低於該值時，批次抓取會把兩者
都壓成一次查詢，驗證因此在「有沒有正確使用 join fetch」兩種情況下都通過，等於沒有守。
唯一例外是無法 join fetch 的查詢（native query），該情形 MUST 在驗證處寫明它守得住什麼、
守不住什麼。

#### Scenario: 扇出增加不改變往返次數
- **WHEN** 同一支對外查詢分別在小扇出與大扇出的資料下執行
- **THEN** 兩次送出的 SQL 筆數 SHALL 相同

#### Scenario: 關聯載入不得逐筆進行
- **WHEN** 查詢結果的每一筆都需要讀取它所指向的實體（公司、品類節點）
- **THEN** 這些實體 SHALL 以一次查詢一併取得，MUST NOT 每筆各查一次

#### Scenario: 圖走訪不得逐節點往返
- **WHEN** 查詢需要沿組成關係走訪多層
- **THEN** 走訪 SHALL 由資料庫一次完成，MUST NOT 每經過一個節點就往返一次

#### Scenario: 驗證本身必須偵測得到關聯載入方式的退化
- **WHEN** 某支查詢的 join fetch 宣告被移除，改為僅依賴全域批次抓取
- **THEN** 驗證 SHALL 失敗
