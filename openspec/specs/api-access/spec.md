# api-access Specification

## Purpose
呼叫端能不能打到這個 API，以及在什麼前提下才可以。目前只涵蓋跨來源（CORS）：
沒有它，前端跑在另一個 port 時連第一支端點都打不到，因此它不是體驗問題而是能不能串接的前提。
本能力同時載明一條刻意接受的風險——**服務目前沒有任何認證授權**——寫在這裡而不只是程式註解，
是因為它會決定跨來源清單能開多寬、以及這個服務能不能部署。日後補上認證授權時，
新的要求也歸在這條能力底下。
## Requirements
### Requirement: 瀏覽器可跨來源呼叫 API

系統 SHALL 允許來自指定來源的瀏覽器跨來源請求，否則前端無法呼叫任何端點。

允許的來源 MUST 可由設定指定，且預設 SHALL 只含本機開發用的來源。
系統 MUST NOT 以萬用字元允許任意來源——即使目前沒有認證機制也一樣：
萬用字元會在日後加上 cookie 或授權標頭時默默變成破口，而那時不會有人回頭想起這個設定。

#### Scenario: 允許清單內的來源可呼叫
- **WHEN** 瀏覽器自允許清單中的來源發出跨來源請求
- **THEN** 系統 SHALL 回應對應的跨來源標頭，使請求得以完成

#### Scenario: 清單外的來源不得取得跨來源許可
- **WHEN** 瀏覽器自不在允許清單中的來源發出跨來源請求
- **THEN** 系統 MUST NOT 回應允許該來源的跨來源標頭

#### Scenario: 允許來源可依環境調整
- **WHEN** 以設定指定一組允許來源
- **THEN** 系統 SHALL 以該組來源為準，不需改動程式碼

### Requirement: 未具備認證前不得對外開放

系統目前**沒有任何認證與授權機制**，包含建立、修正、審核與批次匯入在內的所有寫入端點
皆為公開可呼叫。

因此允許的跨來源清單 MUST NOT 放寬至不受控的來源，且本服務在補上認證授權之前
MUST NOT 部署至公開網路。此限制為刻意接受的已知風險，非疏漏；
移除此限制的前提是先建立認證授權能力。

#### Scenario: 寫入端點目前不受保護
- **WHEN** 任何呼叫端對寫入端點發出請求
- **THEN** 系統目前 SHALL 照常處理——此即為何本服務不得對外開放
